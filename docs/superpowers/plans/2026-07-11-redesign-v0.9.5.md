# Grimport v0.9.5 — Complete Redesign + Feature Pack — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Ship the full macOS-native redesign and the proposed feature set as a single release, **v0.9.5**.

**Architecture:** Rebuild the vanilla HTML/CSS/JS frontend from the ground up against the delivered design canvas, in phases that keep the app bootable between commits. Backend changes are additive (new routes/tables), guarded by the existing auth model from v0.9.0. Every phase ends bootable and, where logic changed, test-covered.

**Design source of truth:** `docs/design/redesign-canvas/grimport-redesign.dc.html` (open in a browser). **Token/component spec:** `docs/design/design-system.md`. **Functional contract per screen:** `docs/superpowers/specs/2026-07-11-design-revamp-brief.md`. **Inventory of current behavior:** captured in the brief.

## Global Constraints

- Runs exclusively in Docker for production (`docker compose up --build supervisor`).
- Frontend stays **vanilla HTML/CSS/JS** — no framework, no CSS framework. No build step.
- Two first-class themes via CSS custom properties on `:root` (light) and `[data-theme="dark"]` (dark). Keep attribute name `data-theme` (canvas uses `data-th` — translate).
- **Match the canvas** as the visual source of truth; **satisfy the brief** as the functional contract. Every screen must implement its empty / loading / error / success states.
- Status = **glyph + label + colour**, never colour alone; colour-blind-safe. Use exact tokens from `design-system.md`.
- Icons are inline SVG. Respect `prefers-reduced-motion` for all motion/skeletons.
- Node test suite (`cd supervisor && npm test`) stays green; add tests for all new/changed backend logic.
- Keep `supervisor/Dockerfile` present. Release via tag `v0.9.5` → GHCR.
- Preserve all existing API behavior and the v0.9.0 authorization model; do not regress security.
- Sample data in the canvas (versions 1.8.2/1.9.0, demo sites) is illustrative — real data comes from the API.

## Sequencing notes

- Phases A→F are the redesign (must go roughly in order; A unblocks all).
- Phase G (bug fixes) can run any time after A; do it before release.
- Phases I (features) are backend-forward and independent of the visual phases — can be interleaved once their Settings tabs (D) exist.
- Between every task the app must boot; visual tasks are verified against the canvas, logic tasks against `npm test` + live smoke.
- Track progress in `.superpowers/sdd/progress-redesign.md`. Final whole-branch review before release (strongest model).
