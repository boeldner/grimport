# Grimport Roadmap — 0.9.0 → 0.9.5 → 1.0

Date: 2026-07-11
Status: Proposed — awaiting approval
Current shipped: **0.9.0** (security + deploy hardening, released to GHCR)

## Vision

Grimport becomes a *round* product: a self-hosted static-site panel that feels
as polished as Netlify/Vercel but runs on your own Docker host. 1.0 means:
safe, reliable, beautiful, and complete enough that a new user can go from
zero to a live HTTPS site in minutes without reading docs.

## Design direction (the 2026 refresh)

**Complete revamp** (user decision, 2026-07-11) — a full redesign of the UI,
not an evolution of the current stylesheet. We rebuild the visual language
from scratch: new layout, new component vocabulary, new type/space/color
system. The brand red (`#b91c1c`) is a starting point, not a constraint —
the revamp may re-anchor the palette. Direction is being chosen from three
built HTML mockups (see `supervisor/public/mockups/`).

Original evolutionary option (kept for reference, NOT chosen): keep dark
surfaces + red accent + existing token system and merely elevate with:

- **Depth & material:** layered surfaces, softer shadows, subtle borders,
  1px inset highlights. Less flat, more tactile.
- **Motion:** purposeful micro-interactions — hover/press states, list
  enter/leave transitions, deploy progress, toast notifications. 150–250ms,
  respects `prefers-reduced-motion`.
- **Space & hierarchy:** more whitespace, a real type scale, consistent
  spacing tokens, clearer primary/secondary action hierarchy.
- **Modern SaaS patterns:** a command palette (⌘K), skeleton loaders, empty
  states with guidance, inline validation, keyboard navigation.
- **System coherence:** every view rebuilt from one component vocabulary
  (cards, tables, badges, buttons, inputs, modals, toasts) so nothing feels
  bolted on.

Non-goals for the refresh: no framework migration (stays vanilla JS/HTML/CSS
per project constraints), no color-identity change, no dependency on a CSS
framework.

## Milestone path to 0.9.5

Each point release is independently shippable and releasable to GHCR. Order
front-loads visible value and fixes known breakage early.

### 0.9.1 — Design-system foundation + UX bug fixes
The groundwork everything else builds on, bundled with the known broken actions.
- Extract a documented design-token + component layer in `style.css`
  (buttons, inputs, cards, tables, badges, modals, toasts, skeletons).
- Add a toast/notification-feedback primitive (replaces silent success/failure).
- Fix the known-broken UI actions from the audit:
  - Activity CSV export link (`/api` prefix missing) → works.
  - Uptime detail view (backend route exists, UI never calls it) → wired up.
  - Notification-event preferences (POST route missing) → implemented + saved.
  - Change-password form (writes legacy key, login ignores it) → points at
    `users` table, actually changes the password.
- No visual overhaul yet beyond the primitives — this is the safety net.

### 0.9.2 — Core views rebuilt on the new system
- Rebuild Sites list, Site detail, Overview/dashboard on the component layer.
- Command palette (⌘K): jump to sites, actions, settings.
- Skeleton loaders + empty states for every list.
- Responsive layout pass (usable on tablet/mobile).

### 0.9.3 — Deploy experience
- Drag-and-drop zip upload with a real upload/extract/build/apply progress UI
  (backend already records stages; surface them live).
- Redesigned deploy history + rollback UI (diff of what changed, one-click
  rollback with confirmation, clear "current" marker).
- Domain aliases: multiple domains per site (www→apex, extra hostnames).
  Requires a `site_domains` table and Traefik multi-host labels.

### 0.9.4 — Operations & trust
- Scoped API tokens in the UI (the role column shipped in 0.9.0 — expose it;
  add per-site scoping + expiry + last-used display).
- Backups: scheduled export of `supervisor.db` + site data to a local path
  and/or S3/R2, with restore instructions and a "download backup now" button.
- Alerting channels beyond the panel bell: email (SMTP) and/or ntfy/Pushover
  for site-down, deploy-failed, cert-expiry.
- Audit-log view: the activity data, filterable, admin-only (backend already
  admin-gated in 0.9.0).

### 0.9.5 — Polish & "round" pass
- Onboarding: first-run wizard (set admin password, base domain, SSL mode).
- Accessibility pass: focus rings, ARIA, keyboard paths, contrast in both themes.
- Consistency sweep: every empty/error/loading state, every toast, every
  confirm dialog reviewed against the system.
- Docs/wiki refresh to match the new UI + the API-Reference gaps from the audit.
- Performance: skeletons, lazy loads, no layout shift.

**0.9.5 = feature-complete UI + reliable ops, ready for a 1.0 hardening cycle.**

## 1.0 — MoSCoW

### MUST have (1.0 ship blockers)
- Everything in 0.9.1–0.9.5, stable and bug-free.
- Security posture maintained (0.9.0 fixes) + the deferred items closed:
  DNS-rebinding connection pinning, reconcile preview-container awareness,
  analytics log-tail OOM guard.
- Self-service password reset OR a documented admin recovery path (today it's
  DB surgery — unacceptable for 1.0).
- Reliable deploys: atomic, observable, rollback-safe (largely done in 0.9.0/0.9.3).
- Scheduled backups + a tested restore path.
- Complete, accurate API reference (audit found ~half the API undocumented).
- First-run onboarding so a fresh install is usable without the wiki.

### SHOULD have (strong value, not blockers)
- Git-based deploys: connect a repo, build on push (webhook or poll), no
  manual zip. The single biggest feature gap vs Netlify/Vercel.
- Per-push/branch deploy previews with automatic preview URLs.
- Email/ntfy alerting (if it slips from 0.9.4).
- A small CLI (`grimport deploy ./dist`) wrapping the API for CI use.
- 2FA (TOTP) for the panel login.

### COULD have (nice, lower priority)
- Static form handling (capture form POSTs from hosted sites — Netlify staple).
- Custom headers/redirects UI polish + import from `_headers`/`_redirects`.
- Deeper analytics: paths, referrers, unique visitors (today: status class + bytes).
- i18n scaffolding (UI is hardcoded English; German first given the audience).
- Team/org roles beyond admin/editor/viewer (per-site collaborators UI).

### WON'T have this cycle (wishlist / post-1.0)
- Edge/serverless functions.
- Multi-server orchestration / clustering.
- A plugin or template marketplace.
- Managed DNS provisioning (currently read-only checker; stays that way).
- Billing/multi-tenant SaaS mode.

## Decomposition & execution model

This roadmap is the anchor. Each point release gets its own spec → plan →
subagent-driven implementation cycle (the same workflow that shipped 0.9.0).
We do NOT try to spec all of 0.9.1–0.9.5 at once.

Immediate next step after roadmap approval: brainstorm + spec **0.9.1**
(design-system foundation + UX bug fixes), because it unblocks every later
visual milestone and fixes user-visible breakage.

## Constraints (carried from the project)

- Runs exclusively in Docker for production.
- Frontend stays vanilla JS/HTML/CSS — no framework, no CSS framework.
- Node.js supervisor, Traefik, SQLite (better-sqlite3), express-session.
- Releases via git tag `v*` → GitHub Actions → GHCR → Arcane pulls to Hetzner.
- Every release keeps `supervisor/Dockerfile` present and the test suite green.

## Open questions for the user

1. Design direction: is **Refined Dark (evolution)** right, or do you want a
   bolder break? (Assumed: evolution.)
2. Backups target: local path only for 0.9.4, or S3/R2 from the start?
3. Git-based deploys: 1.0 MUST or SHOULD? (Assumed SHOULD — it's large and can
   follow 1.0 without blocking a solid release.)
4. i18n: is German UI wanted for 1.0, or is English fine? (Assumed English for
   1.0, i18n post-1.0.)
